## 1. Resumen ejecutivo

El sitio está construido sobre **Wix Editor con Velo habilitado**, publicado bajo dominio personalizado y con plan Premium. El ecosistema combina:

- Página web corporativa.
- Wix Bookings para reservas.
- Wix Stores para catálogo y productos.
- Wix Blog para contenidos.
- Formularios y pagos.
- Tarjetas regalo.
- Área privada de miembros.
- Facturación mediante Wix Invoices.
- Wix Hotels.
- Herramientas SEO.

La plataforma es adecuada para un negocio de peluquería y estética con reservas online, venta de productos, contenidos y servicios complementarios. El principal foco técnico debe estar en mantener una **separación clara entre catálogo de servicios, reservas, pagos, clientes y contenido**, evitando duplicar información entre CMS, Bookings y Stores.

El CMS puede actuar como capa de presentación, clasificación o enriquecimiento, pero no debería sustituir a los identificadores nativos de Bookings, Stores o Payments.

### 4.2 Identificadores

Se recomienda conservar los identificadores nativos de Wix:

- `serviceId` para servicios.
- `bookingId` para reservas.
- `contactId` para contactos.
- `memberId` para miembros.
- `productId` para productos.
- `variantId` para variantes.
- `orderId` para pedidos.
- `paymentId` para pagos.
- `invoiceId` para facturas.
- `addonId` para complementos.

Los nombres visibles pueden estar en español, pero los identificadores técnicos y contratos internos deben permanecer en inglés y alineados con la API correspondiente.

## 5. Wix Bookings

### 5.1 Áreas críticas

Debe verificarse periódicamente:

- Servicios visibles y reservables.
- Duración real de cada servicio.
- Personal asignado.
- Horarios de trabajo.
- Bloqueos de calendario.
- Capacidad.
- Antelación mínima de reserva.
- Política de cancelación.
- Política de reprogramación.
- Servicios de una fase y de dos fases.
- Complementos disponibles.

### 5.2 Flujo recomendado de reserva

```text
1. Resolver servicio mediante slug o identificador.
2. Obtener configuración real del servicio.
3. Consultar disponibilidad.
4. Mostrar horarios al cliente.
5. El cliente selecciona fecha, hora y, opcionalmente, profesional.
6. Revalidar disponibilidad inmediatamente.
7. Crear la reserva.
8. Crear o asociar el proceso de pago.
9. Confirmar el estado real de la reserva.
10. Enviar comunicación al cliente.
```

La creación de un checkout no debe considerarse automáticamente una reserva confirmada.

### 5.3 Estados recomendados

```text
PENDING
AVAILABLE
CONFLICT
FAILED
RESERVED
PAID
CONFIRMED
COMPENSATED
```

La aplicación debe distinguir entre:

- Disponibilidad consultada.
- Reserva creada.
- Pago iniciado.
- Pago confirmado.
- Reserva confirmada.
- Compensación ejecutada tras un fallo parcial.

### 5.4 Selección de profesional

Reglas recomendadas:

- Si el cliente elige profesional, utilizar exclusivamente ese profesional o devolver conflicto.
- Si no lo elige, seleccionar el profesional con menor carga de horas reservadas ese día.
- Resolver empates mediante rotación.
- Mantener la lógica en backend.
- No permitir que el frontend determine la disponibilidad definitiva.

### 5.5 Servicios de dos fases

Para servicios con dos fases:

```text
duración total =
fase 1 +
tiempo de exposición +
fase 2
```

Debe validarse:

- `allowCombine`.
- `linkedPhases`.
- Intervalo entre fases.
- Personal compatible.
- Disponibilidad de ambas fases.
- Creación coordinada de las dos reservas.

Las dos reservas deben tratarse como una operación coordinada, con compensación si solo una de ellas se crea correctamente.

## 6. Wix Stores

El sitio utiliza **Wix Stores Catalog V1**.

### Recomendaciones:

- Mantener el contrato V1 mientras sea la versión activa; no introducir una migración parcial a V3 antes del ADR, la adaptación completa y las pruebas.
- Mantener productos físicos separados de servicios reservables.
- No duplicar precios de Stores en colecciones CMS salvo como caché controlada.
- Validar inventario desde la fuente nativa.
- Usar variantes nativas para tamaño, formato o presentación.
- Evitar que el frontend calcule precios finales.
- Validar productos y variantes en backend antes de crear pedidos o pagos.

### Riesgos habituales:

- Producto visible en CMS pero no disponible en Stores.
- Variante sin inventario.
- Precio desactualizado en una colección auxiliar.
- Producto eliminado con referencias huérfanas.
- Mezcla de `productId`, `variantId` y campos personalizados.

## 7. Pagos, pedidos y facturación

### 7.1 Separación de estados

Debe mantenerse la siguiente separación:

```text
Checkout creado
≠
Pago autorizado
≠
Pago capturado
≠
Pedido creado
≠
Reserva confirmada
≠
Factura emitida
```

### 7.2 Recomendaciones

- Registrar los identificadores reales devueltos por Wix.
- No usar el identificador del proveedor externo como si fuera el identificador de Wix.
- No confirmar una reserva únicamente porque existe un checkout.
- Implementar reintentos idempotentes.
- Registrar errores parciales.
- Definir una estrategia de compensación.

### 7.3 Facturación

Wix Invoices está instalado, pero debe confirmarse la versión activa antes de desarrollar integraciones específicas. El código de facturación no debe asumir la misma estructura que Payments o Orders.

## 8. CMS y contratos de datos

### 8.1 Recomendación de modelo

Las colecciones CMS deberían dividirse en:

#### Catálogo de servicios enriquecido

Campos recomendados:

```text
serviceId
slug
name
title
description
duration
price
mainMedia
recomendaciones
clientHidden
allowCombine
linkedPhases
addonId
```

#### Complementos

```text
addonId
name
title
description
price
duration
active
```

#### Configuración de servicios duales

```text
serviceId
phase1ServiceId
phase2ServiceId
exposureDuration
allowCombine
linkedPhases
```

### 8.2 Convenciones

- `addonId` identifica complementos.
- `addOnIds` debe reservarse para el array de transporte hacia Wix Bookings.
- Los valores de `addOnIds` deben ser `addonId`.
- `name`, `title` y `addonId` deben estar alineados entre módulos.
- No crear IDs alternativos si Wix ya proporciona uno nativo.
- Las etiquetas visibles pueden estar en español; los nombres técnicos, en inglés.

### 8.3 Integridad referencial

Cada referencia a una entidad nativa debe validarse:

```text
CMS service record
  └── serviceId válido en Wix Bookings

CMS addon record
  └── addonId válido

CMS product record
  └── productId válido en Wix Stores
```

Debe existir una rutina de auditoría para detectar:

- Servicios inexistentes.
- Complementos eliminados.
- Productos sin correspondencia.
- Slugs duplicados.
- Registros activos sin precio.
- Duraciones inválidas.
- Relaciones de fases incompletas.

## 9. Backend y frontend

### Backend

Responsable de:

- Resolver entidades nativas.
- Consultar disponibilidad.
- Seleccionar personal.
- Revalidar horarios.
- Crear reservas.
- Validar precios.
- Gestionar pagos.
- Aplicar compensaciones.
- Registrar errores.
- Aplicar reglas de negocio.

### Frontend

Responsable de:

- Presentar servicios.
- Mostrar disponibilidad recibida.
- Recoger datos del cliente.
- Mostrar estados.
- Gestionar navegación.
- No decidir disponibilidad final.
- No confiar en precios enviados desde el navegador.
- No crear reservas sin revalidación backend.

### Regla principal

> El frontend propone; el backend valida y confirma.

## 10. Seguridad

### Recomendaciones prioritarias

- No exponer secretos ni credenciales en código del navegador.
- Mantener operaciones sensibles en backend.
- Validar todos los identificadores recibidos.
- Validar permisos de usuario y miembro.
- Sanitizar contenido HTML o rich text.
- Controlar abuso de endpoints públicos.
- Limitar frecuencia de consultas de disponibilidad.
- No confiar en precios, descuentos o estados enviados por el cliente.
- Registrar eventos sin almacenar datos sensibles innecesarios.

### Datos personales

El sistema maneja potencialmente:

- Nombre.
- Email.
- Teléfono.
- Historial de reservas.
- Pagos.
- Facturas.
- Preferencias de servicios.

Debe aplicarse minimización de datos y evitar duplicar información personal en CMS si ya existe en Contacts o Members.

## 16. Conclusión

El sitio dispone de una base funcional sólida y de los módulos necesarios para operar reservas, productos, pagos, contenidos y clientes. El área de mayor riesgo no es la cantidad de aplicaciones, sino la coordinación entre ellas.

La prioridad técnica debe ser:

1. Mantener una fuente de verdad por entidad.
2. Usar siempre los identificadores nativos.
3. Separar disponibilidad, reserva y pago.
4. Ejecutar las reglas sensibles exclusivamente en backend.
5. Evitar mezclar Catalog V1 con Catalog V3.
6. Formalizar los contratos CMS.
7. Añadir trazabilidad, idempotencia y compensación.
8. Auditar periódicamente las referencias entre CMS, Bookings y Stores.

Este informe representa una **evaluación arquitectónica basada en el contexto confirmado del sitio**. Para convertirlo en una auditoría de código completa sería necesario revisar adicionalmente las colecciones CMS, módulos Velo, permisos, funciones backend, páginas dinámicas, automatizaciones y registros de errores.

## 4. Hallazgos principales

### H-01 — Portada pública en estado “Muy pronto”

**Severidad:** Crítica.  
**Estado:** Confirmado mediante lectura pública.

La página principal devuelve un mensaje de próxima apertura. Si el objetivo es operar reservas, venta y captación orgánica, esta portada reduce la utilidad del sitio y puede impedir que Google y los usuarios encuentren la oferta real.

**Acciones:**

1. Confirmar la página definida como inicio.
2. Comprobar si existe una versión publicada distinta de la prevista.
3. Revisar redirecciones, reglas de navegación y posibles páginas splash.
4. Verificar en incógnito y en móvil después de publicar.
5. Solicitar nueva indexación cuando el contenido definitivo esté disponible.

### H-02 — Enlaces sociales posiblemente incorrectos

**Severidad:** Alta.  
**Estado:** Confirmado en la portada recuperada.

Los enlaces observados apuntan a perfiles genéricos de Wix. Esto provoca pérdida de tráfico, confianza y señales locales.

**Acción:** sustituirlos por los perfiles oficiales y probar cada enlace en escritorio y móvil.

### H-03 — Descripción SEO genérica e insuficiente

**Severidad:** Alta.  
**Estado:** Confirmado.

La descripción “MUY PRONTO | Marian Madrid” no explica servicios, ubicación ni propuesta de valor. Debe reemplazarse por una descripción única orientada a intención local y conversión.

### H-04 — Riesgo de incompatibilidad de versiones

**Severidad:** Crítica.  
**Estado:** Confirmado.

En el corte auditado, Stores utiliza Catalog V1 e Invoices utiliza V1. Mantener contratos homogéneos mientras esas versiones estén activas. La migración de Stores a Catalog V3 y cualquier cambio de Invoices requieren decisiones separadas, migración explícita y pruebas; la migración a V3 está pendiente, no completada.

### H-05 — Riesgo transaccional entre reserva, checkout y pago

**Severidad:** Crítica.  
**Estado:** Riesgo arquitectónico.

La creación de un checkout no demuestra que la reserva esté confirmada ni que el pago se haya completado. El sistema debe modelar estados separados, revalidar disponibilidad y disponer de compensación.

### H-06 — Riesgo de duplicación entre CMS y aplicaciones nativas

**Severidad:** Alta.  
**Estado:** Riesgo arquitectónico.

Servicios, precios, productos, clientes y estados no deben tener varias fuentes maestras. El CMS debe enriquecer o presentar información, no sustituir de forma accidental a Bookings, Stores, Contacts o Payments.

```text
Presentación Wix Editor
  ├── páginas públicas

  ├── widgets personalizados
  └── área de miembros

Frontend Velo
  ├── estado de interfaz
  ├── validación básica de experiencia
  ├── navegación
  └── llamadas a servicios backend

Backend Velo
  ├── autorización
  ├── reglas de negocio
```

- Los errores de un sistema externo deben mapearse a errores de negocio propios.
- Los IDs nativos deben conservarse sin traducción ni duplicación arbitraria.
- Las integraciones deben admitir reintentos sin crear duplicados.

## 7. Auditoría de reservas

### 7.1 Flujo canónico

```text
RESOLVE_SERVICE
→ LOAD_CONFIGURATION
→ CHECK_AVAILABILITY
→ USER_SELECTION
→ EXACT_REVALIDATION
→ CREATE_RESERVATION
→ CREATE_CHECKOUT_OR_CONFIRM
→ VERIFY_PAYMENT
→ CONFIRM_BOOKING
→ NOTIFY
```

Disponibilidad y creación deben ser pasos separados. Para comprobar disponibilidad debe utilizarse `locationType: "BUSINESS"`; para crear la reserva, `locationType: "OWNER_BUSINESS"`.

### 7.2 Estados

```text
PENDING
AVAILABLE
CONFLICT
FAILED
RESERVED
PAID
CONFIRMED
COMPENSATED
```

Cada transición debe registrar fecha, operación, entidad, resultado y causa de error.

### 7.3 Asignación de personal

- Si el cliente selecciona profesional, se usa ese profesional o se devuelve conflicto.
- Si no lo selecciona, se asigna quien tenga menos horas reservadas ese día.
- En empate, se aplica rotación determinista.
- La decisión se ejecuta en backend.
- Debe revalidarse justo antes de crear la reserva.

### 7.4 Servicios duales

```text
totalDuration = phase1Duration + exposureDuration + phase2Duration
```

Validaciones obligatorias:

- `allowCombine`.
- `linkedPhases`.
- Separación entre fases.
- Compatibilidad de personal.
- Disponibilidad de ambas fases.
- Coordinación de dos reservas simples.
- Compensación si solo se crea una fase.

### 7.5 Idempotencia

Cada intento debe incorporar una clave estable derivada de la sesión o intención de reserva. Antes de crear una nueva entidad, el backend debe comprobar si esa intención ya produjo una reserva o checkout.

## 22. Criterios de aceptación del ecosistema

El ecosistema puede considerarse técnicamente sano cuando:

1. La portada pública corresponde al estado comercial real.
2. Todos los enlaces públicos tienen destino correcto.
3. Cada entidad posee una única fuente de verdad.
4. CMS y código comparten contratos versionados.
5. Disponibilidad y creación están separadas.
6. Toda creación revalida disponibilidad.
7. La asignación de personal cumple las reglas acordadas.
8. Los servicios duales compensan fallos parciales.
9. Checkout, pago, reserva y confirmación son estados distintos.
10. Los reintentos no crean duplicados.
11. Stores utiliza el contrato de la versión activa: actualmente Catalog V1; migrar a Catalog V3 solo después de ADR, implementación integral y pruebas.
12. Facturación usa únicamente Invoices V1.
13. No hay secretos ni reglas críticas en frontend.
14. Los permisos CMS aplican mínimo privilegio.
15. Existen trazas correlacionadas y alertas.
16. Los recorridos críticos tienen pruebas.
17. SEO, accesibilidad y rendimiento cumplen objetivos medidos.
18. La documentación permite mantener el sistema sin conocimiento tribal.

## 23. Conclusión

El sitio cuenta con una base tecnológica capaz de soportar una operación digital completa, pero la amplitud del ecosistema aumenta el riesgo de inconsistencias entre CMS, Bookings, Stores, pagos y facturación. El hallazgo inmediato es la exposición pública de una portada “Muy pronto”, acompañada de metadatos mínimos y enlaces sociales que deben verificarse.

La prioridad no es añadir más funcionalidad, sino asegurar que lo existente tenga contratos claros, estados verificables, fuentes únicas de verdad y pruebas reproducibles. La siguiente fase recomendada es una auditoría de implementación: inventario real de código y colecciones, revisión de permisos, pruebas de reservas y pagos, mediciones de rendimiento y accesibilidad, y cierre con evidencias antes/después.
